# Frontend interaction foundation — design / contract / implementation tickets

## Inspection and domain model

`app/runtime/engine.py` owns `ask(session_id, text)` and commits through `ConversationManager` to SQLite. Pending clarification is a `Clarification(question, options: list[str], goal_id, requirement_id?, need_id?)`; a subsequent `ask` on that session re-enters the interpreter with the original query. There is no FastAPI, browser, OpenAPI, event callback or server-side run object. `GoalStatus` is COMPLETE/LIMITED/FAILED/WAITING_FOR_USER. Judge support IDs identify accepted internal Artifacts. `DATABASE_RESULT.structured_data` includes typed rows/schema plus sensitive SQL/IR. `AnswerPackage` in `app/response/answer_contract.py` is the internal composer navigation contract. Python dependencies are pip/requirements.txt; no JS package manager exists (choose npm with lockfile). See ADR 0033.

## Interaction states

Idle → send command → running/status → terminal COMPLETE/LIMITED/FAILED or WAITING_FOR_USER. WAITING emits a structured clarification card, not a chat message. Answering submits an opaque option ID or allowed free text; backend checks exact pending clarification and passes its own original option text to the existing clarification path. The new run emits resolution then progress/approved result. Earlier turns persist in thread. Supported result A may remain visible when B blocks a new turn; within one turn, only Judge-approved artifact IDs may be projected. No browser ambiguity detector. Transport failure, malformed data and backend failure are separate from a valid LIMITED answer.

## Wire contract v1

`POST /api/conversations` → `{conversation_id}`. `GET /api/conversations/{id}` → text history and pending clarification (persisted) plus current in-process run events when available. `POST /api/conversations/{id}/messages` `{text}` → `{message_id, run_id}` (202). `POST /api/conversations/{id}/clarifications/{clarification_id}/responses` `{selected_option_ids: string[], free_text?: string}` → `{message_id, run_id}` (202); invalid/stale IDs and concurrent commands are 409/422. `GET /api/runs/{run_id}/events` → `text/event-stream` with `id: <run_id>:<sequence>`, `data: <JSON AgentEvent>`; `Last-Event-ID` or `?after=` replays strictly subsequent events. Invalid cursor is rejected. Each `AgentEvent` contains `version: 1, type, id, conversation_id, run_id, message_id, timestamp, payload`; goal/artifact IDs appear where applicable. `run.started`, `message.accepted`, `agent.status`, `assistant.delta`, `clarification.required`, `clarification.resolved`, `artifact.created`, `answer.partial`, `answer.completed`, `run.failed`. Known payloads validated; unknown type fallback is non-authoritative.

`ClarificationRequest`: `id, conversation_id, run_id, goal_id, question, reason, blocking_requirement_ids, options[{option_id,label,description?}], allow_free_text, status`. Opaque option IDs map to server-held option texts; labels are never parsed into semantic IDs in the browser. `ClarificationResponse` carries only IDs/free text. `AnswerView`: goal_id, status (including forward-compatible PARTIAL), text, limitations, backend-classified execution issues, requirements[{id,statement,coverage,required}], artifacts. `PresentationArtifact`: id/type/title/description/status/evidence_refs/scope/calculation/payload; types text, metric, table, chart, evidence, warning. Table payload: columns[{id,label,kind,unit?,format?}], rows of JSON scalars, default_sort?, total_rows?, pagination?; chart: kind bar/line/scatter, typed axes/series and scalar records. Presentation artifact is derived exclusively from accepted Judge support artifacts, stripping execution internals. Do not accept arbitrary JSX/HTML/SQL/JS.

SSE is append-only and idempotent: reducer dedupes by event ID; one complete answer delta has stable message ID; reconnect sends last seen ID. After completion stream closes. If network closes early, reconnect; if recovery fails report transport error without deleting prior content. The in-process log is bounded by process lifetime; reopening a persisted conversation reconstructs text/pending clarification, not historical table events. Default view shows answer/status/table/clarification; evidence refs expand on demand. Developer mode can show structured Requirement coverage and IDs but not raw traces.

## Component model

`ConversationPage` owns thread and commands; `useRunEvents` handles SSE and reducer with event dedupe; `ClarificationCard` is accessible controlled form; `AnswerView` renders backend status and preserved artifacts; `ArtifactRenderer` dispatches typed envelope to `TableView` (TanStack sorting/filter/visibility/paging) and `ChartView` (Recharts bar/line/scatter). `ErrorNotice` distinguishes structured API error and malformed event. React Router has `/conversation/new` and `/conversation/:id`. TanStack Query fetches snapshots; component reducer handles ephemeral stream. Tailwind/shadcn-inspired accessible primitives, no baseball-specific logic in generic components.

## Tickets and acceptance order

1. Write failing FastAPI contract tests: commands, replay, pending/resolved/stale clarification, supported-only table, partial retention and structured errors. Implement API models/projector/run adapter with narrow CORS and no secrets.
2. Write failing reducer/Zod/component tests: duplicate delta, unknown/invalid events, clarification keyboard/forms/pending/resolved, partial preservation and table sorting/filter. Implement React shell, router, Query, TanStack Table, Recharts and styles.
3. Add Playwright real-API flow(s), run with available database/provider; record environment-dependent blockers rather than invent backend states. Repair failed tests and inspect security/review boundary. Report actual evidence in docs/audit/FRONTEND_INTERACTION_FOUNDATION.md.

Production packaging is deferred: static Vite assets + Python API under same-origin reverse proxy; alternatively separately hosted static origin with explicit CORS, or containerize both later. No Docker requirement for development.
